Project 02 — Linux Server Setup & Web Deployment on EC2

How I launched a hardened Ubuntu Linux server on AWS EC2 — configuring security groups, IAM roles, key pairs, deploying Nginx via user data, and monitoring with CloudWatch.

Daniel Ayodele AWS Cloud Engineer & Cybersecurity Enthusiast
EC2IAMSecurity GroupsNginxCloudWatchSSMBeginner

Project 01 taught me how to host a static site on S3 and serve it through CloudFront. That was a great start, but it felt incomplete. Everything was files sitting in a bucket. For Project 02, I wanted to get into actual compute — a real Linux server running in the cloud that I could configure, access, and watch work. EC2 was the obvious next step, and this is the story of how that went.

What I Was Building

The idea was straightforward: launch an Ubuntu server on EC2 and have it serve a web page automatically when it boots, without me having to SSH in and manually install anything. I also wanted to do it properly — not just click through the default settings, but actually set up a dedicated security group, attach an IAM role with the right permissions, and monitor the instance through CloudWatch.

Simple enough on the surface, but there were a few moving parts that needed to come together in the right order.

Step 1 — Building the Security Group

Before touching the instance itself, I created a security group. This is basically the firewall that sits in front of your EC2 instance and decides what traffic gets in and what doesn't. I named it Project2-web-server-sg and added three inbound rules to cover what I needed:

SSH on port 22, but only from my own IP address. HTTP on port 80, open to anyone. And HTTPS on port 443, also open, for when I eventually add SSL. That SSH restriction is something I've seen overlooked a lot — opening port 22 to the whole internet is a quick way to get your server hammered by bots. Even if your key pair is secure, there's no reason to expose it widely.

Worth knowing: Create a separate security group for each project or workload. Sharing one security group across multiple instances makes permissions messy and hard to audit later.

Step 2 — Setting Up the IAM Role

This was the part I was most curious about going in. The instinct for a lot of people learning AWS is to just give an instance an access key — copy the credentials into a config file and move on. That approach works, but it's the wrong way to do it. If those credentials ever leak, you have a serious problem.

The right approach is an IAM role attached directly to the instance. The instance gets temporary credentials automatically, rotated by AWS behind the scenes, and you never have to manage long-lived keys. For this project, the role Project2-EC2-Role needed two things: permission to push metrics to CloudWatch, and permission to connect through Session Manager so I wouldn't need to expose SSH at all for day-to-day access.

IAM Roles page showing Project2-EC2-Role created with trusted entity set to AWS Service: ec2

Keep in mind: Never attach AdministratorAccess to an EC2 role. Only grant the permissions the instance actually needs to do its job — nothing more.

Step 3 — Creating the Key Pair

Even with Session Manager available, I still created a key pair. It's good practice to have SSH access as a fallback, and the process itself is worth understanding. I created an RSA key pair named project2-key in .pem format — AWS downloads it once, and if you lose it, there's no way to recover it. It lives on your machine and nowhere else.

When you actually use it, you set the file permissions before connecting:

SSH Access
chmod 400 project2-key.pem
ssh -i project2-key.pem ubuntu@<PUBLIC_IP>

Key pairs console — project2-key created, RSA type, fingerprint confirmed

Step 4 — Launching the Instance

With the security group, IAM role, and key pair ready, launching the instance was relatively quick. Ubuntu 22.04 LTS on a t3.micro, everything wired up in the network settings, and then the most interesting part — the user data script.

User data runs automatically on first boot, as root, before anything else happens. I used it to install and start Nginx so the web server would be live the moment the instance became reachable, without any manual steps from me:

user-data.sh (simplified)
#!/bin/bash
apt-get update -y
apt-get install -y nginx
systemctl start nginx
systemctl enable nginx

Instance launch success — instance ID i-03e584273bbfa8ded confirmed

The big idea: User data is a simple but powerful form of Infrastructure as Code. The server builds itself at launch. No SSH session required, no manual setup, no room for human error during deployment.

Step 5 — The Server Goes Live

A few minutes after launch, the instance hit the Running state and showed 3/3 status checks passed. I copied the public IP, opened a browser tab, and there it was — the Nginx welcome page loading over HTTP. The user data script had done exactly what it was supposed to do.

EC2 dashboard — project2-web-server running, t3.micro, 3/3 checks passed, Public IP: 52.91.82.33

Nginx default page live at http://52.91.82.33 — web server up and serving from first boot

That feeling: Watching a server come online and serve traffic on its own, without touching it after clicking launch, was genuinely satisfying. That's what automation is supposed to feel like.

Step 6 — Checking CloudWatch

Once the server was live, I pulled up CloudWatch to see what the numbers looked like. CPU had spiked to around 18% during the initial boot and user data execution, then dropped right off once everything settled. Network in showed 42 MB during that same window — the apt package downloads for Nginx. After that, traffic was just the occasional test hit I was making from the browser.

None of this was surprising, but seeing it in actual graphs made the boot sequence feel tangible. You could literally watch the instance start up.

Why this matters: You can't manage what you can't see. Even a simple server needs visibility into what it's actually doing so you can catch problems early and understand your baseline before anything goes wrong.

What Didn't Go Smoothly

I initially forgot to enable auto-assign public IP, which would have left the instance sitting in the VPC with no way to reach it from the internet. Caught it before launching, thankfully. The status checks also showed 2/2 for a minute before settling on the correct 3/3 — just a timing lag, but it's the kind of thing that can make you panic if you haven't seen it before.

The other thing that caught me was the SSH key permissions. The first time I tried to connect, the SSH client threw an error because the .pem file was too open. Running chmod 400 on it fixed it immediately, but it's not obvious if you've never seen that error before.

The Bigger Picture

What this project made clear is that EC2 is never just a virtual machine. Every instance sits at the intersection of networking, identity, automation, and observability. Get any one of those layers wrong and things either don't work or aren't secure. Getting them all right, even on something as simple as a single web server, is good practice for everything that comes later.

Honest takeaway: User data automation was the most satisfying part of this whole project. Watching a server configure and serve traffic on its own after launch is the moment where Infrastructure as Code stops being a concept and starts feeling real.
