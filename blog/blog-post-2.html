Project 02 — Linux Server Setup & Web Deployment on EC2

How I launched a hardened Ubuntu Linux server on AWS EC2 — configuring security groups, IAM roles, key pairs, deploying Nginx via user data, and monitoring with CloudWatch.

Daniel Ayodele AWS Cloud Engineer & Cybersecurity Enthusiast
EC2IAMSecurity GroupsNginxCloudWatchSSMBeginner

After completing Project 01 — hosting a static portfolio on S3 and CloudFront — the natural next step was to work with compute. In Project 02, I launched a hardened Ubuntu Linux server on Amazon EC2, configured it with a proper security group, attached an IAM role, and deployed a live web server using EC2 user data. This project introduced me to the core of cloud compute infrastructure.

Project Overview

The goal was to build and deploy a secure, functional Linux web server entirely through the AWS Management Console. Rather than clicking through defaults, I deliberately configured every component — security, access control, networking, and automation — from scratch.

The server runs Nginx, is accessible publicly on port 80, and is monitored through CloudWatch. Secure terminal access is available via AWS Session Manager with no SSH key required.

Step 1 — Creating the Security Group

A security group is the first line of defence for any EC2 instance — it acts as a virtual firewall controlling inbound and outbound traffic at the instance level. I created a dedicated security group named Project2-web-server-sg with three inbound rules:

  • SSH (port 22) — restricted to My IP only for secure remote access
  • HTTP (port 80) — open to 0.0.0.0/0 for public web access
  • HTTPS (port 443) — open to 0.0.0.0/0 for future SSL traffic

Restricting SSH to My IP rather than opening it to the world is a basic but critical security practice. If your IP changes, you update the rule — you never expose port 22 to everyone.

Best Practice: Always create a dedicated security group per project or workload. Sharing security groups across multiple instances makes it harder to apply least-privilege rules and audit access.

Step 2 — Creating the IAM Role

Instead of embedding credentials in the server, I attached an IAM role to the EC2 instance. This is the AWS-recommended approach — the instance inherits permissions automatically through the instance profile, with no long-lived access keys required.

The role Project2-EC2-Role was created with two managed policies attached:

  • CloudWatchAgentServerPolicy — allows the instance to push metrics and logs to CloudWatch
  • AmazonSSMManagedInstanceCore — enables Session Manager for browser-based terminal access

IAM Roles console — Project2-EC2-Role created and visible with trusted entity set to AWS Service: ec2

Security Note: Never attach AdministratorAccess to an EC2 role. Always follow the principle of least privilege — grant only the specific permissions the instance actually needs.

Step 3 — Creating the Key Pair

For SSH access, I created an RSA key pair named project2-key in .pem format. The private key is downloaded once at creation and must be stored securely — AWS does not store it and it cannot be recovered if lost.

After downloading, SSH access requires setting correct file permissions:

SSH Access
chmod 400 project2-key.pem
ssh -i project2-key.pem ubuntu@<PUBLIC_IP>

Key pairs console — project2-key created, RSA type, fingerprint confirmed

Step 4 — Launching the EC2 Instance

With the prerequisite resources in place, I launched the EC2 instance configured as follows:

  • Name: project2-web-server
  • AMI: Ubuntu Server 22.04 LTS
  • Instance type: t3.micro (within free tier)
  • Key pair: project2-key
  • Security group: Project2-web-server-sg
  • IAM instance profile: Project2-EC2-Role
  • User data: Nginx installation and startup script

The user data script runs automatically at first boot, installing Nginx and configuring it to serve on port 80 — no manual SSH session required for the initial deployment.

user-data.sh (simplified)
#!/bin/bash
apt-get update -y
apt-get install -y nginx
systemctl start nginx
systemctl enable nginx

Instance launch success — instance ID i-03e584273bbfa8ded initiated successfully

Key Insight: EC2 user data scripts are a simple but powerful form of Infrastructure as Code. The server configures itself at launch — no manual intervention needed after clicking "Launch instance".

Step 5 — Instance Running and Web Server Live

After a few minutes, the instance reached the Running state with 3/3 status checks passed. I copied the Public IPv4 address and opened it in a browser to confirm the Nginx server was live and serving traffic.

EC2 Instances dashboard — project2-web-server running, t3.micro, 3/3 checks passed, Public IP: 52.91.82.33

Nginx default page live at http://52.91.82.33 — web server installed and working via user data automation

Milestone: The server was live and serving HTTP traffic within minutes of launch — with zero manual SSH setup. The entire Nginx deployment was automated through the user data script.

Step 6 — Monitoring with CloudWatch

With the IAM role granting CloudWatch permissions, the instance automatically reported metrics to CloudWatch. I reviewed two sets of monitoring data from the EC2 console:

  • CPU utilization — peaked at 18.3% during initial startup, then settled
  • Network in/out — showed 42.86 MB inbound during the user data install phase
  • CPU credit balance and usage — visible for the t3.micro burstable instance type
  • Network packet counts — confirmed HTTP traffic reaching the server
Why CloudWatch Matters: Without monitoring you are flying blind. Even a simple web server needs visibility into CPU usage, network traffic, and status checks to detect problems early and plan capacity correctly.

Challenges I Encountered

A few things required troubleshooting during this project:

  • The instance initially showed 2/2 status checks — one check lagged behind; waiting two minutes resolved it
  • I temporarily forgot to enable auto-assign public IP, which would have left the instance unreachable from the internet
  • The user data script runs as root, so package paths and permissions needed to be considered carefully
  • SSH access required setting chmod 400 on the .pem file — without this, the SSH client rejects the key

Each of these small friction points deepened my understanding of how EC2 networking, IAM, and Linux permissions work together.

Key Takeaways

This project reinforced that cloud compute is not just about launching a virtual machine. Every EC2 instance sits at the intersection of networking (security groups), identity (IAM roles), automation (user data), and observability (CloudWatch). Getting each layer right is what separates a properly configured server from a misconfigured one.

Takeaway: EC2 user data is one of the most practical skills in cloud engineering. Automating server configuration at launch removes human error from the deployment process and makes infrastructure reproducible.
