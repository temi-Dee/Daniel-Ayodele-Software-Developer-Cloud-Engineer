Project 04 — RDS PostgreSQL with Automated Backups

How I built a private PostgreSQL database on Amazon RDS with Multi-AZ redundancy, automated backups, a bastion host, and CloudWatch alarms.

Daniel Ayodele AWS Cloud Engineer & Cybersecurity Enthusiast
Amazon RDSPostgreSQLVPCMulti-AZEC2CloudWatch

Projects 01 through 03 moved from static hosting, to a Linux server, to a serverless workflow. Project 04 brought me back to infrastructure, but with a different responsibility: storing data that needs to survive. I wanted a database that was private by default, backed up automatically, and able to fail over without me rebuilding a server. Amazon RDS was the right tool for that job.

What I Was Building

The goal was a managed PostgreSQL database that application traffic could reach privately, while administrative access came through a small bastion host in a public subnet. The database itself would sit in two private subnets in different Availability Zones, with Multi-AZ enabled for high availability.

That sounds like a lot of pieces, but each one has a clear job. The VPC provides the boundary, security groups control who can talk to what, RDS manages the database, and the bastion gives me a controlled route in for testing.

Step 1 — Creating the VPC and Subnets

I started with a dedicated VPC named RDS-VPC using the 10.0.0.0/16 range. The database needed subnets in two Availability Zones, so I created private subnets for RDS in us-east-1a and us-east-1b. I also created a separate public subnet for the bastion host.

The important detail is that the database does not need a public IP. The public subnet exists for the bastion, while the RDS subnet group uses only the two private subnets. That separation is the foundation of the network design.

Step 2 — Giving the Bastion a Route Out

To make the bastion reachable, I attached an internet gateway to the VPC and created a route table with a default route to it. That route table is associated with the public subnet only. The RDS subnets stay private, so there is no direct path from the internet to the database.

Small network, clear boundaries: A public subnet is not a reason to make the database public. It is simply where the controlled entry point lives. The RDS security group still decides whether database traffic is allowed.

Step 3 — Separating SSH and Database Access

I created two security groups: Bastion-SG and RDS-SG. Bastion-SG allows SSH on port 22 from my current IP address. RDS-SG allows PostgreSQL traffic on port 5432 only when the source is Bastion-SG.

That second rule is better than putting an IP address directly into the database rule. The database trusts the bastion as a workload, not the whole internet or an address that may change later.

Two security groups created for the project: Bastion-SG for SSH and RDS-SG for PostgreSQL

Keep port 5432 private: Opening PostgreSQL to 0.0.0.0/0 would expose the database to unnecessary scanning and attack attempts. Referencing the bastion security group keeps the rule narrow.

Step 4 — Creating the RDS Subnet Group

RDS uses a DB subnet group to know where it is allowed to place database resources. I added the two private subnets to rds-subnet-group, one in each Availability Zone. Once AWS marked the group as complete, the network layer was ready for the database instance.

rds-subnet-group completed successfully with the private subnets selected for RDS

Step 5 — Launching PostgreSQL on RDS

For the database, I chose PostgreSQL 15, enabled storage encryption, set a seven-day backup retention period, and kept public access disabled. Multi-AZ was the key setting: RDS maintains a standby in another Availability Zone and handles failover if the primary becomes unavailable.

After waiting for the managed service to finish provisioning, my-postgres-db reached the Available state. That was a useful reminder of the difference between launching infrastructure and managing it. I did not need to install PostgreSQL, configure replication, or write backup jobs. RDS took care of those operational tasks.

my-postgres-db available in Amazon RDS, running the PostgreSQL engine

The useful shift: The database is still infrastructure, but I am not responsible for keeping the database software alive. My responsibility is the surrounding design: network access, credentials, backups, monitoring, and sensible permissions.

Step 6 — Connecting Through the Bastion

Once the bastion was running, I connected to it over SSH and installed the PostgreSQL 15 client. From there, the private RDS endpoint resolved normally because the bastion and database were inside the same VPC. The connection used TLS, and PostgreSQL confirmed that the client was talking to the expected server version.

psql installed on the bastion and connected successfully to the private RDS endpoint

Connect from the bastion
sudo yum install postgresql15 -y
psql -h <RDS_ENDPOINT> -U dbadmin -d postgres

Step 7 — Testing the Database and Backups

I created a small testdb database, added a users table, inserted sample rows, and queried them back. It was deliberately simple, but it verified the full path: workstation to bastion, bastion to private RDS endpoint, and SQL execution inside PostgreSQL.

Automated backups were enabled with a seven-day retention period. I also configured CloudWatch alarms for high CPU utilization and low free storage so the database would have a basic operational safety net instead of relying on me to remember to check it manually.

End-to-end database test passing: testdb, the users table, and sample records returned from PostgreSQL

What Needed the Most Attention

The most important decisions were not inside the SQL commands. They were made before the first connection: keeping RDS private, placing it in subnets across two Availability Zones, and allowing port 5432 only from the bastion security group. Those choices determine the database's exposure long before an application sends its first query.

The bastion also made the connection flow easier to understand. At first I tried typing the database hostname directly into the shell, which of course treated it like a command. Once I used it as the host argument to psql, the connection worked. A small mistake, but a good reminder that infrastructure work is often about using the right value in the right context.

The Bigger Picture

This project changed how I think about a database in the cloud. It is not just a PostgreSQL endpoint. It is a combination of placement, access rules, resilience, recovery, and monitoring. RDS removes a lot of repetitive server maintenance, but it does not remove the need to design carefully.

The best part was being able to test real SQL against a database that was never exposed publicly. That made the security model practical instead of theoretical: private networking did not stop me from working, it just made the route to the database intentional.

Real takeaway: High availability is not one checkbox. It is the result of several decisions working together: multiple Availability Zones, private subnets, controlled access, backups, and monitoring that tells you when the system needs attention.

What's Next

The next useful step would be connecting an application to this database without putting credentials in code, then exploring IAM authentication, Secrets Manager, and a private application tier. For now, the core result is solid: a private PostgreSQL database, a controlled administrative path, and a recovery plan running in the background.
