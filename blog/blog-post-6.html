Project 06 — Infrastructure as Code with Terraform

How I turned an AWS VPC, EC2, and RDS stack into reusable Terraform modules with remote state and repeatable deployments.

Daniel Ayodele AWS Cloud Engineer & Cybersecurity Enthusiast
TerraformInfrastructure as CodeAWS VPCEC2RDSRemote State

Projects 01 through 05 taught me how to build AWS resources and automate application delivery. Project 06 changed the question from “Can I create this?” to “Can I recreate this reliably?” I used Terraform to describe a complete AWS stack in code: a VPC, public and private subnets, an EC2 instance, and an RDS PostgreSQL database. The result was infrastructure I could review, apply, change, and destroy without rebuilding it by hand in the console.

The Problem I Wanted to Solve

Creating resources manually works for learning, but it becomes difficult to trust once there are many settings to remember. A missed route, an incorrect subnet, or a security group rule can leave two environments subtly different. Terraform gives those decisions a home in version-controlled configuration.

I also wanted the state file to live remotely. Terraform needs state to understand what it manages, so storing that state in an encrypted, versioned S3 bucket with DynamoDB locking makes collaboration and recovery much safer than keeping one local file on my laptop.

Services and Technologies Used

Tool or Service Purpose
Terraform Defines, plans, applies, and tracks the AWS infrastructure
Terraform Modules Separates VPC, EC2, and RDS resources into reusable components
Amazon VPC Provides the network, subnets, routes, gateway, and security groups
Amazon EC2 Runs the web instance created by the EC2 module
Amazon RDS Runs the PostgreSQL database inside private subnets
S3 and DynamoDB Store and lock Terraform's remote state

How the Terraform Project Fits Together

Module Structure
terraform-project/
  ├── backend.tf       # Remote S3 state and locking
  ├── main.tf          # Provider and module calls
  ├── variables.tf     # Shared inputs
  ├── outputs.tf       # Useful resource values
  └── modules/
      ├── vpc/          # Network and security groups
      ├── ec2/          # Web instance and IAM profile
      └── rds/          # PostgreSQL and DB subnet group

Step 1 — Writing the Configuration

I began with the root module files and a terraform.tfvars file for environment values. The configuration included the AWS region, CIDR ranges, Availability Zones, instance types, and database settings. The resource definitions stayed in modules so the root module could focus on wiring the system together.

Seeing the variables and modules together made the design easier to reason about. Instead of one long file that mixed every resource, each module had a clear boundary and a small set of inputs and outputs.

Terraform project open in VS Code while the modular infrastructure configuration is being applied

Step 2 — Building the VPC Module

The VPC module created the network foundation: the VPC itself, public and private subnets across two Availability Zones, an internet gateway, a public route table, and security groups. The public subnets were intended for the web instance, while the private subnets gave RDS a controlled network location.

This was the first place where Terraform’s declarative model became useful. I described the desired relationships, and Terraform worked out the order needed to create them.

The Terraform-created VPC visible in the AWS console with its generated VPC ID and available state

Public and private subnets created across the configured Availability Zones

Step 3 — Applying the Full Stack

Once the modules were connected, I ran terraform apply. Terraform acquired the remote state lock and began creating the resources in dependency order. The terminal output made the process easy to follow: IAM resources completed first, the VPC and subnets followed, then the database and compute resources continued provisioning.

There is something satisfying about watching a complete environment appear from a plan. The output also made the wait times honest. RDS took longer than the network resources, and Terraform kept the state of the operation visible while it worked.

Terraform apply in progress as the VPC, IAM, EC2, and RDS modules create their resources

Successful apply completed with 18 resources added and the key infrastructure outputs returned

The important moment: The environment was no longer a collection of console clicks. It was represented by code that could be reviewed and applied again, with Terraform explaining exactly what changed.

Step 4 — Inspecting State and Verifying AWS

After the apply completed, I used Terraform outputs and state commands to inspect what had been created. I also checked AWS directly: the EC2 instance was running, and the RDS database had reached the available state with a private endpoint.

This two-sided verification matters. Terraform confirms what it believes it manages, while the AWS console and CLI confirm the resources are healthy in the provider itself.

Post-apply verification showing the running EC2 instance and available RDS database returned by AWS CLI queries

Step 5 — Making a Change Safely

Infrastructure as code becomes most useful after the first deployment. I changed an input value and ran terraform plan again. Terraform showed the intended update, the unchanged attributes, and the values that would be known only after apply.

That preview creates a useful pause before a change reaches AWS. Instead of guessing which resources a manual edit might affect, I could review the proposed action first and apply the exact plan only when it made sense.

Review before apply: Terraform is powerful because it can change real infrastructure. Always inspect the plan, protect remote state, and keep database credentials out of committed variable files.

What Needed the Most Attention

The most important design decision was separating reusable modules from environment-specific values. That kept the configuration understandable and made it possible to change an instance type or CIDR range without hunting through unrelated resources.

Remote state was another lesson. State is not just a cache; it is Terraform’s record of ownership and relationships. Versioning the S3 bucket and locking updates with DynamoDB gives that record a recovery path and helps prevent two changes from colliding.

The Bigger Picture

Terraform did not remove the need to understand AWS. It made my AWS decisions more visible. I still had to choose the network layout, security boundaries, instance settings, and database placement, but those decisions were now written down and repeatable.

That is the real value of infrastructure as code for me: not simply faster provisioning, but a clearer relationship between an architectural decision and the resources that implement it.

Real takeaway: The best Terraform workflow is deliberately boring: write the configuration, validate it, review the plan, apply it, verify the result, and destroy what you no longer need.

What's Next

The next step is to add environment separation, stronger secret handling, and CI checks for Terraform formatting and validation. The foundation is ready: the AWS stack can be reviewed, recreated, changed safely, and managed from code.
