Project 03 — Serverless Contact Form with Lambda and SES

How I built a fully serverless email pipeline using API Gateway, AWS Lambda, and Amazon SES — no EC2, no servers to manage, just a function that runs when someone clicks Submit.

Daniel Ayodele AWS Cloud Engineer & Cybersecurity Enthusiast
LambdaAPI GatewaySESIAMNode.jsCORSCloudWatch

Projects 01 and 02 both involved infrastructure you could see and touch — an S3 bucket, a CloudFront distribution, an EC2 instance running Nginx. Project 03 took a different turn. No servers. No instances. No SSH. Just code that runs in response to an HTTP request and disappears the moment it's done. This is what serverless actually means, and building it from scratch made the concept click in a way that reading about it never did.

The Problem Worth Solving

A contact form sounds trivial, but think about what it actually needs to do. A user fills in their name, email, and message. They click Submit. Something needs to receive that data, validate it, and send it as an email to someone. The traditional answer is a server running PHP or Node.js sitting there 24/7 waiting for submissions.

The serverless answer is cleaner: an API endpoint triggers a Lambda function only when a form is submitted. Lambda validates the input and hands it to Amazon SES to send the email. Nothing runs when there's nothing to do. You pay per execution, not per hour.

Step 1 — Verifying the Email in SES

Before Lambda can send any email, SES needs to know that you actually own the address you're sending from. In sandbox mode — which is where every new account starts — both the sender and the recipient address have to be verified. You add an email identity, AWS sends a verification link to that inbox, and once you click it, SES trusts the address.

It's a small step but an easy one to trip over if you forget. I tried testing the function before clicking the verification link on my first attempt, got an error, then realised what I'd missed.

Amazon SES identity — verification is pending and the confirmation email must be opened before sending

Sandbox vs production: In sandbox mode you can only send to verified addresses. When you're ready to send to real users, you apply for SES production access through the console. For testing, sandbox is fine.

Step 2 — The IAM Role for Lambda

Lambda functions don't have permissions by default. You have to explicitly tell AWS what the function is allowed to do, and you do that through an IAM role. The role ContactFormLambdaRole needed two things: the basic Lambda execution policy so it could write logs to CloudWatch, and an inline policy granting it permission to call ses:SendEmail and ses:SendRawEmail.

Getting this right before creating the function saves a lot of back-and-forth. If the role is missing permissions, Lambda will execute but SES will reject the call and you'll get a permissions error buried in the CloudWatch logs.

Scope it tightly: The SES policy here uses "Resource": "*" for simplicity, but in a production setup you'd lock it down to a specific verified identity ARN so the function can only send from one address.

Step 3 — Creating the Lambda Function

With the role ready, I created the Lambda function ContactFormHandler on Node.js 18.x, attached the IAM role, and then wrote the handler code directly in the console editor. The function does three things: parses the incoming JSON body from API Gateway, runs basic validation on the name, email, and message fields, then calls SES to send the email if everything checks out.

Two environment variables handle the email addresses — SENDER_EMAIL and RECIPIENT_EMAIL — so the function itself contains no hardcoded values. Change the addresses without touching the code.

lambda/index.js (core logic)
const { SESClient, SendEmailCommand } = require("@aws-sdk/client-ses");
const ses = new SESClient({ region: process.env.AWS_REGION });

exports.handler = async (event) => {
  const { name, email, message } = JSON.parse(event.body);

  if (!name || !email || !message) {
    return { statusCode: 400, body: JSON.stringify({ error: "Missing fields" }) };
  }

  await ses.send(new SendEmailCommand({
    Source: process.env.SENDER_EMAIL,
    Destination: { ToAddresses: [process.env.RECIPIENT_EMAIL] },
    Message: {
      Subject: { Data: `Contact form: ${name}` },
      Body: { Text: { Data: `From: ${name} (${email})\n\n${message}` } }
    }
  }));

  return { statusCode: 200, body: JSON.stringify({ success: true }) };
};

Step 4 — Setting Up API Gateway

Lambda on its own has no public URL. API Gateway is what gives it one. I created a REST API named ContactFormAPI, added a /contact resource, and created a POST method with Lambda proxy integration enabled. That proxy setting is important — it passes the full HTTP request object to Lambda as-is, which is what lets the function read the form data from event.body.

The other thing that needed setting up was CORS. Because the form is on a static HTML page hosted somewhere else (a different origin), the browser will block the request unless the API returns the right headers. I added an OPTIONS method with the correct Access-Control-Allow-Origin headers, deployed to a prod stage, and the endpoint was live.

API Gateway — ContactForm REST API created and listed in the AWS console, ready for its resources and methods

CORS explained simply: When your HTML page at domain A tries to call an API at domain B, the browser checks whether domain B allows it. CORS headers are how domain B says yes. Forgetting them produces a confusing error that looks nothing like a permissions problem.

Step 5 — Testing It End to End

Once the API was deployed, I tested it with a curl request before even touching the HTML form. That's a habit worth building — verify the backend works on its own before trying to debug both the frontend and backend at the same time.

Test with curl
curl -X POST "https://<API_ID>.execute-api.us-east-1.amazonaws.com/prod/contact" \
  -H "Content-Type: application/json" \
  -d '{"name":"Test User","email":"test@example.com","message":"Hello from Project 3"}'

The response came back with "success": true and the email landed in the inbox within seconds. That's the moment the whole thing snaps into place — a static HTML page, an API endpoint, a function, and an email service all talking to each other without a single server involved.

The moment it clicks: Watching an email arrive that was triggered by a curl command — passing through API Gateway, through a Lambda function, through SES — is when serverless stops being an abstract concept and becomes something real you understand.

What Tripped Me Up

A few things needed sorting out during this project. The first was the SES verification — easy to miss if you're moving quickly. The second was CORS. I had the POST method working perfectly from curl, but when I tested from the browser form, it was blocked. The browser sends an OPTIONS preflight request before the actual POST, and I hadn't set up the OPTIONS method correctly. Once that was fixed, the browser requests went through cleanly.

The third thing was Lambda permissions. At one point I accidentally attached the wrong role and the function could execute but couldn't call SES. The error came back as an AccessDenied exception in CloudWatch. Having logs available made it straightforward to diagnose — without them, that kind of error is very hard to chase down.

Why Serverless Changes How You Think

After two projects managing infrastructure — an S3 bucket with a CloudFront distribution, then an EC2 server — going serverless felt like a mental shift. There's no instance to worry about patching. No server to monitor for uptime. No capacity to pre-provision. You write a function, give it permissions, and connect it to a trigger. AWS handles everything else.

For a contact form that might receive ten submissions a day, running a server 24/7 to handle that load is genuinely wasteful. Lambda costs next to nothing for that kind of traffic and requires zero maintenance. That's the tradeoff serverless is making, and for the right use cases it's a compelling one.

Real takeaway: The hardest part of this project wasn't the code — the handler is maybe 30 lines. It was understanding how API Gateway, Lambda, SES, IAM, and CORS all connect and in what order to set them up. Getting that sequence right is the skill.

What Comes Next

Project 03 introduced the core serverless building blocks. From here the natural progression is to go deeper — adding DynamoDB to store form submissions, using Lambda layers to manage shared dependencies, and eventually building a full REST API with multiple endpoints. But those are later projects. For now, the pipeline works, the emails arrive, and I understand exactly why.
