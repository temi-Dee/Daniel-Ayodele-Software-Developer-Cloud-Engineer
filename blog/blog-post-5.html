Project 05 — CI/CD Pipeline with GitHub Actions

How I automated testing and deployment for a Node.js application with GitHub Actions, AWS OIDC authentication, S3, and CloudFront.

Daniel Ayodele AWS Cloud Engineer & Cybersecurity Enthusiast
GitHub ActionsCI/CDAWS OIDCS3CloudFrontNode.js

Projects 01 through 04 taught me how to build and connect AWS infrastructure. Project 05 focused on what happens after the infrastructure exists: how code moves from my laptop to a deployed environment without a manual checklist every time. I built a small Node.js API, added tests and linting, then connected GitHub Actions to AWS so every push could be checked automatically and a successful build could be deployed.

The Problem I Wanted to Fix

Manual deployments are easy to accept when a project is small. Run the tests, copy the files, update the bucket, and hope nothing was forgotten. The problem is that this process depends on memory, and memory is not a very reliable deployment system.

The goal here was simple: every change should go through the same steps. GitHub Actions would install the dependencies, run ESLint, run Jest, authenticate with AWS without storing long-lived access keys, and deploy only when the checks passed.

Services and Technologies Used

Tool or Service Purpose
GitHub Actions Runs the CI checks and deployment workflow on every push
AWS IAM OIDC Lets GitHub Actions request temporary AWS credentials without stored access keys
Amazon S3 Stores the deployment artifacts and serves the static site
Amazon CloudFront Distributes the deployed content through a CDN
Node.js and Express Provides the sample application and its API endpoints
Jest and ESLint Tests the application and checks code quality before deployment

Step 1 — Scaffolding the Application

I started with a setup script that created a small Express application, a Jest test suite, an ESLint configuration, and the GitHub Actions workflow files. The point was not to build a complex product. It was to have enough real code for the pipeline to lint, test, and deploy.

Running the script also initialized the local Git repository. Seeing the project files appear and the first test pass made the workflow feel tangible before AWS was involved.

The setup script completed successfully: dependencies were installed, tests passed, and the Git repository was initialized

Step 2 — Provisioning the AWS Side

The AWS configuration script created the resources the workflow needed: an S3 bucket, a CloudFront distribution, an IAM role for GitHub Actions, and the GitHub OIDC provider. It also attached a focused inline policy so the workflow could deploy without receiving broad administrator permissions.

The most important part was the trust relationship. Instead of saving an AWS access key in GitHub, the IAM role trusts tokens issued by GitHub Actions for the repository. Those credentials are temporary and disappear when the workflow ends.

AWS provisioning completed: the S3 bucket, CloudFront distribution, IAM role, and least-privilege OIDC policy were created

Why OIDC matters: A deployment workflow should not depend on a permanent access key that can be copied or accidentally exposed. OIDC gives the workflow short-lived credentials tied to its identity and repository context.

Step 3 — Looking Inside the Generated Project

The setup script generated the application and workflow files in a predictable structure. The application lived under my-app, with source code, tests, package metadata, and separate workflow definitions for checking and deploying the project.

This separation helped me see CI and CD as related but different responsibilities. CI answers whether the code is healthy. CD handles moving that healthy code to AWS.

Generated project structure showing the application files, GitHub workflow files, package configuration, and initialized repository

Step 4 — Watching GitHub Actions Run

After pushing the project, GitHub Actions began running the workflows automatically. The Actions page showed the pipeline history, including successful CI runs and failed deployment attempts while I was correcting the configuration.

That history was useful in its own way. A failed run is not just a red icon; it gives you a timestamp, commit, branch, and logs to work from. Once the workflow was corrected, the successful run became evidence that the complete process could execute from a clean push.

GitHub Actions history showing CI/CD workflow runs, including a successful CI pipeline and deployment runs under review

Failures are part of the feedback loop: A pipeline that fails visibly is more useful than a manual deployment that fails silently. The important thing is to read the job logs, fix the smallest configuration issue, and run the same workflow again.

Step 5 — Testing Before Deployment

Before trusting the workflow, I ran the tests locally. The Jest suite checked the root response, the health endpoint, and the API information endpoint. The test run also produced a coverage report, which made it clear what the current test suite covered and what it did not.

I also ran ESLint separately. This is a small habit, but it makes debugging easier: when a workflow fails, I know whether the problem is code quality, application behavior, AWS authentication, or deployment itself.

Local Jest run passing all three API tests with coverage output recorded for the application

Step 6 — Checking the App Locally

With the tests passing, I started the Express server and checked the endpoints from the browser. The response confirmed that the application was listening on port 3000 and returning the expected JSON payload.

This local check matters because a green deployment pipeline cannot rescue an application that does not behave correctly. The workflow verifies repeatability; the application tests verify behavior.

The Express application running on localhost:3000, with the browser returning the expected CI/CD Pipeline JSON response

Step 7 — Cleaning Up AWS Resources

After testing, I ran the cleanup script. It disabled and removed the CloudFront distribution, emptied and deleted the S3 bucket, deleted the IAM role, and removed the GitHub OIDC provider. Cleaning up is part of the project, not an optional extra, especially when the resources can continue generating charges after the experiment is finished.

Cleanup completed successfully: the CloudFront distribution, S3 bucket, IAM role, and OIDC provider were removed

What Needed the Most Attention

The hardest part was not writing the workflow YAML. It was understanding the trust boundary between GitHub and AWS. The workflow needed permission to request credentials, the IAM role needed to trust the right GitHub identity, and the deployment policy needed to be narrow enough to avoid turning CI into an administrator.

The failed runs also reinforced a practical lesson: troubleshoot the stage that failed. If Jest passes but AWS authentication fails, there is no value in rewriting the application. The pipeline makes those boundaries visible, which is exactly what good automation should do.

The Bigger Picture

CI/CD is often described as a productivity feature, but this project made it feel more like a reliability and security feature. The pipeline creates a repeatable path for changes, records what happened, and prevents a deployment from skipping the checks that protect it.

Using OIDC was the most important design choice. Automation should not require permanent secrets when a workload identity can provide temporary access instead. That idea will matter even more as the applications and AWS environments become larger.

Real takeaway: A deployment pipeline is not just a set of commands moved into YAML. It is a shared agreement about what must be true before code reaches production: tests pass, linting passes, credentials are temporary, and every run leaves an audit trail.

What's Next

The next step would be adding stronger branch protection, dependency and security scanning, environment-specific approvals, and a deployment preview. The foundation is now there: a small application can be tested, deployed, monitored through workflow history, and cleaned up through automation.
